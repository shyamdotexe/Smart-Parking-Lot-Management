================================================================================
B. COMPOSITION  (object created AND owned internally; lifecycle bound)
================================================================================
Result: NO composition relationships exist between domain classes.

Reasoning (checked, not assumed):
- ParkingLot.floors / Floor.spots / Floor.availableSpots hold references to
  Floor and ParkingSpot objects that are created OUTSIDE the owner and injected
  through addFloor(...) / addSpot(...). The owner therefore does not create them,
  so this is aggregation (section C), not composition.
- Ticket.vehicle and Ticket.spot are supplied via the constructor - also not
  created by Ticket -> plain association.
- Ticket.exitTime is created inside `settle` via the passed LocalDateTime - a
  library type, not a domain composition.
- The only objects genuinely instantiated inside owners are the COLLECTIONS:
    Floor       : `new ArrayList<>()`, `new PriorityQueue<>()`
    ParkingLot  : `new TreeMap<>()`, `new HashSet<>()`, `new HashMap<>()`
  These containers are owned by their class, but their ELEMENTS are shared with
  other objects (e.g. a ParkingSpot is in both Floor.spots and Floor.availableSpots),
  so the element relationship is aggregation, not composition.
- Special case: ParkingLot creates and holds itself (`INSTANCE`), a static
  self-association implementing the Singleton pattern. In Mermaid: ParkingLot --> ParkingLot

C. AGGREGATION  (externally created object stored/reused; owner does not create it)
================================================================================
Class A o-- Class B | Evidence | Cardinality
--------------------+----------+------------
ParkingLot o-- Floor     | `addFloor(Floor floor)` stores a caller-created Floor in `floors`; the CLI builds the Floor objects, ParkingLot never `new Floor(...)`. No removal/deletion API owns the lifecycle. | 1 o-- 0..* (0 before any addFloor; 2 in the CLI setup; tests reset to 0)
Floor o-- ParkingSpot    | `addSpot(ParkingSpot spot)` stores a caller-created spot in `spots` AND offers the same object to `availableSpots`. Floor never `new ...Spot(...)`. | 1 o-- 0..* (spot count varies; 3 on floor 1, 4 on floor 2 in the CLI)
  (note: the SAME ParkingSpot instance is referenced twice inside Floor -
   once in the `spots` list and (while free) once in the `availableSpots`
   priority queue. This is a shared aggregation, not two relationships.)

  "the whole owns its parts for the lifetime of the app" as composition, you could
  render them as composition instead - this is a modelling-style choice, NOT a
  source-code fact. Source-code fact: the owner does not instantiate the part.
- Everything else is directly evidenced and requires no review.
- No relationship is marked REQUIRES REVIEW as a correctness uncertainty.
