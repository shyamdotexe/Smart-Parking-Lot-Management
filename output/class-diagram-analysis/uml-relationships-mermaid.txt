UML-READY RELATIONSHIP DATA (Mermaid syntax)

Notation used:
  A <|-- B   generalization / extends
  A <|.. B   realization / implements
  A *-- B    composition
  A o-- B    aggregation
  A --> B    association
  A ..> B    dependency
  A <-- B    association (reverse direction, drawn only when clearer)

PART 5 - RECOMMENDATION
================================================================================
Two layouts are viable:
  Option 1 - ONE complete project class diagram (Part 3). Best for showing the
             full architecture in one figure; 20 production types is still
             readable in Mermaid with the classes collapsed.
  Option 2 - SEPARATE diagrams per module (Part 4a-4f). Better for explaining
             each concern (vehicles, spots, core, billing, tickets, CLI).

Suggested final report approach: use Part 3 as the master overview, then include
4a (vehicle), 4b (spot) and 4c (core) as zoomed-in views, because those three
modules carry the real inheritance/aggregation structure. Billing (4e) and
ticket (4d) are small enough to keep as insets.
